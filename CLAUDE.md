## What this is
A web application that answers tax-law questions for professionals (accountants, tax lawyers, auditors) in Armenia, grounded in official legal texts from arlis.am (ARLIS — the official legal information system of Armenia, where legal acts are officially published). Answers must cite exact laws and articles with links to the source. This is an information/search tool, NOT legal advice — every answer carries that framing.

**v1 scope: Tax vertical — plus the Labour Code since 2026-08-23.** Tax Code of Armenia (Հարկային օրենսգիրք) + related government decisions and SRC (КГД / ՊԵԿ) orders. Web only. Single-user auth is enough for now (simple email login or even a shared password gate).

> ⚠ **The tax-only boundary was crossed deliberately.** Labour/payroll is ~24% of real traffic and 40% of hard failures, and tax-only retrieval cannot reach it at any quality. Measured cost to tax retrieval: zero. See `docs/DECISIONS.md` — it also records why a *distant* domain is cheap to add while near-miss documents are expensive, which bears on any further vertical.

## Core principles (non-negotiable)
1. **Grounding:** The LLM answers ONLY from retrieved article texts. If retrieval doesn't cover the question, the system says so explicitly and shows nearest related articles instead of improvising.
2. **Verbatim quotes:** Quoted law fragments are extracted programmatically from stored article text (string slicing by model-selected offsets or exact-match validation), never regenerated by the model. Armenian original is the authoritative quote; Russian shown alongside when available.
3. **Freshness:** Every document carries status (in_force / repealed / suspended) and last-amendment date. Repealed norms are filtered out of retrieval. UI shows "corpus last synced" and per-document "current as of".
4. **Evaluability:** Retrieval is a pure function `question -> ranked article IDs`, runnable offline against a golden question set with recall@k metrics.

## Tech stack
- **Backend:** Node.js + TypeScript, Fastify
- **DB:** PostgreSQL 16 + pgvector extension + Postgres FTS (tsvector) for keyword search. ONE database for everything: documents, articles, versions, embeddings, sessions.
- **Scraper:** Node + Playwright (ARLIS may need JS rendering; fall back to plain fetch + cheerio where possible). Polite: rate-limited (1 req/2s), identifiable User-Agent, runs off-peak.
- **Embeddings:** API-based to start (no self-hosting in v1). Default: OpenAI text-embedding-3-large. Abstract behind an `Embedder` interface so BGE-M3 / Voyage can be swapped later.
- **Reranker:** Cohere Rerank v3 (multilingual) via API, behind a `Reranker` interface.
- **Generation LLM:** Anthropic API. Claude Sonnet-class for answer generation; Claude Haiku-class for cheap steps (query contextualization, issue extraction). Behind an `LLM` interface.
- **Frontend:** React + TypeScript (Vite). Chat-style UI but designed as a professional workbench, not a toy chatbot (see UI section).
- **Session store:** Postgres tables (no Redis in v1).

## Language strategy
**REVISED after the milestone-2 audit. The corpus is Armenian-only.**

The original plan assumed ARLIS publishes Russian and English translations and
that we would embed Russian when fresh. It does not. Measured across the 21-document
tax corpus: **hy 21/21, ru 0/21, en 0/21**. The `/ru/` and `/en/` URL prefixes
translate site chrome only — act bodies and even act titles stay Armenian, and
the pages return HTTP 200, so missing translations are detectable only by script
detection, never by status code.

- **Storage:** `text_hy` is the only populated text column. `text_ru` / `text_en`
  stay in the schema (nullable) for a possible machine-translation layer later,
  but nothing writes them in v1.
- **Retrieval is cross-lingual by construction.** Users ask in Russian, Armenian
  and mixed; every vector in the index is Armenian. Query-side language handling
  is therefore not a refinement — it is the thing that makes retrieval work at all.
- **Embedding model choice is a primary risk, not a detail.** It must be chosen
  by measurement, not reputation, because Armenian is low-resource.
- **Generation reads Armenian directly.** No translation step before the LLM.
  Answer in the user's language; Armenian quotes stay Armenian and are extracted
  programmatically as verbatim substrings.
- **The freshness guard is moot** and stays unimplemented: with no translations
  there is no `ru_amended_at` to compare against `hy_amended_at`. Keep the
  columns; do not build the comparison until a translation source exists.
- **Armenian tokenisation cost is unavoidable.** The plan to hold Russian text in
  LLM context to save 3–5x on tokens is not available. Budget accordingly.

### Milestone 5 embedding benchmark — required design
The benchmark must measure the retrieval path that actually ships:
**Russian-language questions against Armenian target articles.** Recall measured
on Armenian questions would validate a path no user takes and would overstate
real performance. Compare at least one OpenAI model against a model with strong
low-resource coverage (BGE-M3, Cohere embed-multilingual-v3), and note that
dimensions differ (3072 vs 1024) — `embeddings.vector` width and its halfvec
HNSW index depend on the winner, so decide before bulk embedding.

## Pipeline A — Ingestion (offline)
1. **Audit script (BUILD THIS FIRST):** given a list of ARLIS document IDs/URLs for the tax corpus, fetch each and report: which language versions exist, their consolidated/amendment dates, whether /latest URL variant works, whether the page structure is parseable. Output a table. This validates all assumptions before the real scraper.
2. **Scraper:** fetch document (all languages), store raw HTML snapshots (keep them — reparse without refetching).
3. **Parser:** split by article using Armenian legal structure (ԳԼՈՒԽ / chapter, Հոդված / article, մաս / part). Preserve tables carefully — tax law is full of rate tables; convert to markdown tables, never flatten to prose. Prepend metadata header to each chunk (law title, article no, status, dates) so chunks are self-contained.
4. **Cross-reference extraction:** regex + LLM pass to find references to other articles; store in article_refs.
5. **Indexing:** embed each chunk (per language strategy above) into pgvector; populate tsvector columns for FTS (Russian and Armenian configs; for Armenian, 'simple' config is acceptable in v1).

## Pipeline B — Update detection (cron)
- **Daily job:** query ARLIS search filtered by publication date (last 7 days, overlapping window). New IDs -> ingest. Classify each new doc: standalone vs amending act (amending acts name their target in the title — parse it). For amended targets: re-fetch consolidated /latest version, diff at article level, re-embed only changed articles. Backstop: probe sequential act IDs above known max.
- **Weekly job:** full re-crawl of the corpus, compare content hashes per language, catch silent updates / late-arriving translations / status changes.
- **Monitoring:** log every run to crawl_log; alert (start with console/email) on: job failure, parse errors on unexpected HTML, or 10+ consecutive days with zero new documents (suspicious silence = detection probably broken).

## Pipeline C — Query answering (online)
1. **Contextualizer** (cheap LLM): input = chat history (last ~8 messages) + fact_summary + new message. Output JSON: { standalone_query, legal_issues[], is_topic_shift, needs_retrieval, updated_fact_summary }. Rewrite conservatively — resolve references from history, NEVER add unstated assumptions. Hypotheticals stay hypothetical.
2. **Fast path:** if the query is a direct article lookup ("текст статьи 265 НК"), skip RAG, return the article directly.
3. **Hybrid retrieval per legal issue:** pgvector cosine top-30 + FTS top-30, merge via reciprocal rank fusion. Filter status = in_force. Expand one hop through article_refs for top candidates.
4. **Rerank** to top 5–8 chunks (merge with session_chunks cache; on topic shift, don't let old cache dominate).
5. **Generation** (strong LLM) with strict system prompt. Fixed answer template:
   - **Короткий вывод** (2–3 sentences, direct answer)
   - **Правовое основание** — per norm: law name + article number (deep link), verbatim Armenian quote of operative fragment (+ Russian alongside if available)
   - **Как это применяется к вашей ситуации** — reasoning with inline article refs
   - **Что важно проверить** — SPECIFIC caution, not boilerplate: name what wasn't covered, adjacent grounds/exceptions in the cited articles, relevant deadlines. Encourage opening full articles.
6. **Confidence gate** using reranker scores + model self-report:
   - confident -> full template
   - partial -> answer grounded parts, ask ONE sharp clarifying question for the rest
   - not_found -> say no direct norm found, list closest related articles clearly labeled as adjacent
7. Log every query with retrieval scores and confidence mode (this is the tuning backlog).

## Answer generation system prompt — requirements to encode
- Answer ONLY from the provided article texts. General legal knowledge may structure the explanation but never supply legal claims absent from provided texts.
- Every legal claim must reference (Law, Article N). No uncited claims.
- Quote selection: output exact substrings of provided texts (validate: quote must be a verbatim substring of the stored article text; if validation fails, drop the quote, keep the reference).
- If provided texts don't answer the question: say so explicitly. Never fill gaps.
- Respond in the user's language; Armenian legal quotes stay Armenian.
- End with the mandatory framing: informational tool, not legal advice, verify the full text of cited articles.

## Frontend (v1)
- Chat input, streamed answers.
- Cited articles render as expandable cards: quoted fragment highlighted inside the full article text, status + "current as of" date, deep link to ARLIS.
- "Related articles" (article_refs neighbors) under each cited card.
- Session list (past conversations).
- Global banner: corpus last synced date + not-legal-advice notice.

## Evaluation
- Seed eval_questions with 50 real tax questions (source them from Armenian accountant Telegram/forum discussions) with known correct article IDs.
- `npm run eval` -> runs retrieval-only against golden set, prints recall@5 and recall@8, per-question misses.
- Every retrieval change (embedding model, chunking, RRF weights, reranker on/off) must be justified by this metric.

## Known risks to keep in mind while coding
- ARLIS has no API; a site redesign is reportedly planned — isolate ALL HTML parsing in one module, keep raw HTML snapshots, fail safe (serve old data, never ingest garbage).
- Translation staleness: Russian/English versions may lag Armenian amendments — always compare amendment dates before trusting a translation.
- Tables in tax law: a mangled rate table = confidently wrong numbers = worst possible failure. Test table extraction explicitly.
- Armenian tokenization is expensive (3–5x) — prefer Russian text in LLM context when fresh, but Armenian quotes are mandatory in output.
